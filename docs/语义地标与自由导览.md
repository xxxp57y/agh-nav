# 语义地标与自由导览（客人想去哪就去哪）

> 这一轮把导航从**指令驱动**改成了**地标驱动**：
> 不再依赖 R2R 的固定指令，客人说去哪就去哪。

---

## 1. 为什么要改，以及发现的关键事实

原来的地标只有每场景 6–8 个，因为是用 R2R 指令文本里提到的地点短语抽出来的。
而"客人想去哪就去哪"要求覆盖整个场景。之前我得出过"这台 habitat 读不到语义区域标注"
的结论 —— **那个结论是错的**，原因是调用方式不对：

| 我之前的写法 | 实际应该 |
| --- | --- |
| `region.category.name`（当属性读） | `region.category.name()` —— 它是**方法** |
| `region.centroid` | 这个字段是空的；位置要从 **object 的 AABB** 取 |

改对之后看到的真相（`scene_inventory.py` / `sem_probe.py`）：

```
每个场景: 20+ region（房间）+ 400+ object（家具）
region  类别: bedroom / bathroom / kitchen / living room / dining room / hallway /
              office / closet / laundryroom / entryway / familyroom / porch / toilet …
object: 每个都带 **AABB 中心** 与 **所属 region**
```

于是地标可以**成体系地生成**，而且不用猜、不用模型编：
`卧室的床`、`厨房的桌子`、`卫生间的洗手池 (2)` —— 房间来自 region，家具来自 object。

## 2. 挖掘流程（`mine_semantic_landmarks.py`）

```
region（房间）+ object（家具，带 AABB 中心与所属 region）
  → 只留"大件"（床/沙发/桌子/洗手池/马桶/浴缸/淋浴/灶台/冰箱/壁炉/楼梯…）
     排除 wall / ceiling / floor / void / cushion / picture / towel（没人会说"带我去靠垫"）
  → AABB 中心 `pathfinder.snap_point()` 吸附到 navmesh 的**可走点**
  → `ShortestPath.find_path()` 验证**真的走得过去**（不是隔墙对望）
  → 同房间内**空间去重**（0.6 m 内视为同一件东西，例如 cabinet 与 counter 常标同一处）
  → 命名：`房间的家具`，同场景重名才加序号
```

产物（`data/landmarks_semantic.json`）：

| 场景 | 地标数 | 房间数 |
| --- | --- | --- |
| `2azQ1b91cZZ` | 61 | 11 |
| `QUCTc6BB5sX` | 50 | 14 |
| `TbHJrupSAjP` | 58 | 14 |
| `zsNo4HB9uLZ` | 43 | 12 |

对比旧做法的 6–8 个，**每场景提升约 6–8 倍**，而且每个点都验证过可达。

## 3. 中文名用大模型批量翻（`translate_landmarks.py`）

MP3D 的类别名是英文（`chest_of_drawers`、`familyroom/lounge`）。做法：

* 把地标表里去重后的 19 个房间词 + 15 个家具词**一次性**发给模型，要求返回严格 JSON；
* 结果缓存到 `data/zh_glossary.json`（**一次翻好、长期复用**，保证命名稳定）；
* 模型返回不合法就重试；最终仍缺的词**保留英文原名**（不硬翻、不编）。

结果：

```
房间: 吧台区 / 卫生间 / 卧室 / 衣帽间 / 餐厅 / 门厅 / 家庭厅 / 走廊 / 厨房 /
      洗衣间 / 客厅 / 休息厅 / 书房 / 其他房间 / 娱乐室 / 楼梯 / 杂物间 / 健身房
家具: 浴缸 / 床 / 柜子 / 椅子 / 五斗柜 / 台面 / 壁炉 / 座位 / 置物架 / 淋浴 /
      洗手池 / 沙发 / 楼梯 / 桌子 / 马桶
```

翻译必须用**家庭日常口语**（`sink→洗手池` 而不是"水槽（洗涤槽）"、
`chest_of_drawers→五斗柜`），提示里给了这些例子。

## 4. 自由导览：走完一程不结束回合

这是行为层面最关键的改动。

**原来的问题**：Habitat 的 VLN 回合在到达**它自己的**终点或超过步数上限后就结束，
之后 `env.step()` 一律被拒（*"Episode over, call reset before calling step"*）。
所以客人派了下一个地方，机器人**一步不动**。旧做法要求用户手动点「重开本轮」。

**现在的做法**（`navlive_server.py`）：

1. 新增 `free_tour` 模式（默认开，`NAVLIVE_FREE_TOUR=0` 可关回回合制）；
2. 走完一程只发 `tour_completed`，**不结束回合** —— 可以立刻接着派下一个地方；
3. 万一 habitat 自己的回合结束了（它的终点/步数上限），`tick()` 里检测
   `episode_finished and plan` 就**原地续一轮**：`env.reset()` 后立刻
   `set_agent_state` 把 agent 放回它**刚才的位置**，继续走剩下航点，并记一条
   `round_advanced` 事件（不瞒着用户）。

**验收**（`free_tour_test.py`，连走三程）：

```
① 语义地标可用（43 个，来自场景标注）: True
② 第一程结束但回合没结束（tour_completed）: True
③ 第二程接着走不重开: True（移动 4.82 m）
④ 第三程继续连: True（移动 1.49 m）
→ 客人想去哪就去哪，一程接一程不用重开 —— 通过
```

## 5. 这一轮踩的坑（都很隐蔽）

| 现象 | 真因 | 修法 |
| --- | --- | --- |
| 地标一直错位/偏少 | `region.category.name` 是**方法**不是属性；`region.centroid` 是空的 | 用 `name()`；位置改从 object 的 AABB 取 |
| 同房间两个地标坐标几乎重合 | 同一件东西被 `cabinet` 与 `counter` 两个类别各标一次 | 同房间内 0.6 m 内**空间去重**，保留优先级高的名字 |
| 走完一程后派下一个地方**不动** | habitat 回合已结束，`env.step()` 被拒 | 自由导览 + 原地续轮（见第 4 节） |
| 续轮**整段失败** | `sim.step("move_forward", 0.0)` —— 这个构建的 `step()` **只接受一个参数** | 改成 `sim.step("move_forward")` |
| 第二程刚起步就报"卡住" | `goto` 没清上一程残留的 `_last_distance`，距离判据被污染 | `goto` 里清 `_last_distance/_last_position/_stall_anchor` |
| 机器人正常小步挪动被误判卡住 | 单步位移判据（<0.02 m）太敏感，实测单步约 0.01 m | 改成**窗口内累计位移**：30 步走不到 0.20 m 才算卡住 |
| 翻译一直 401 | `read_key` 把 `--key-file` 的**路径本身**当成了密钥 | 拆开 `--key` 与 `--key-file` 两个参数 |
| 翻译报 `KeyError: '"rooms"'` | 提示词里的 JSON 花括号被 `str.format` 当占位符 | 写成 `{{` `}}` 转义 |
| 地标出现重名 | 翻译时按英文名加的序号被覆盖掉 | 编号改为翻译后按"同场景是否重名"统一加 |

## 6. 自由导览曾经"机器人不动"—— 根因与修复（重要）

用户反馈："输入指令后机器人压根没动，第一人称画面没在动，轨迹也没有。"
排查下来是**三层原因叠在一起**，每层单独看都像是"不动"，所以很难定位：

### 6.1 第一层：`sim.step()` 用错，把整段焦点切换搞崩了

为了"不经过 `env.step` 就刷新渲染"，我写过：

```python
self.env.sim.step("move_forward")          # ❌ AssertionError: No action move_forward in action space
self.env.sim.step("move_forward", 0.0)     # ❌ TypeError: step() takes 2 positional arguments
self.env.sim.step({"action": "move_forward"})  # ❌ TypeError: list indices must be integers
```

这个环境的 `sim.step()` **三种写法都不通**。而且它的异常被 `focus()` 的
`except Exception` 吞掉，于是**整个焦点切换（包括把 agent 移回该会话位姿）都没执行** ——
表现就是"界面看着对、机器人却不动、也没有轨迹"。

**修法**：改用 `sim.get_observations_at(position=..., rotation=..., keep_agent_at_new_pose=True)`
（按位姿取观测、不推进回合，实测正确）。并且给 `focus()` 加了
`focus_error` 字段 —— **失败必须能被看见**，不能再静默。

### 6.2 第二层：`ShortestPathFollower` 的 stop_distance 太大（这是"卡住"的主因）

`ShortestPathFollower(env.sim, 0.5, ...)` 里的 **0.5 是停止距离**：它离目标还有
0.5 m 就返回 STOP。而我们的到达判据是 0.45 m，两者几乎贴在一起 —— 于是出现：

* 机器人走到 0.5~0.7 m 时 follower 就 STOP；
* 我们判"还没到"（>0.45），继续要动作；
* follower 再返回 STOP …… 反复，位置几乎不动；
* 30 步窗口内累计位移 <0.20 m → 判**停滞** → 计划被清空 → 看起来"派了活但不动"。

**修法**：`ShortestPathFollower(env.sim, 0.2, ...)`。实测立竿见影：

```
12.07 → 5.61 → 0.37 → 0.08（24 秒到达，全程 12+ 步持续推进）
三程验收：20.7s / 12.5s / 8.3s
step 被拒 = 0    tick 出错 = 0    focus 失败 = 0
```

### 6.3 第三层：不要试图自己实现物理（试过，失败）

为了让自由导览不受 habitat 回合语义影响，我试过绕开 `env.step`，直接
`set_agent_state` + 四元数相乘来前进/转身。**这条路走不通**，两个最小复现都验过：

| 坑 | 现象 |
| --- | --- |
| `quat_from_coeffs` 期望 **[w,x,y,z]**，而 `set_agent_state` 期望 quaternion 对象或 **[x,y,z,w]** | 格式混用 → 朝向整个乱掉 |
| `quat_to_angle_axis` 对偏航四元数返回"180° 绕某个倾斜轴" | 据此重建会完全转错方向 |
| 即使修好单次转向，**连续转向**的 yaw 会出现 +15°/+137°/+152°/0° 的异常循环 | 机器人原地打转 |

结论写在 `_apply_action` 的注释里：**动作一律交回 `env.step()`**，它是唯一正确的
物理/朝向实现；回合结束由"原地续轮"兜住。

### 6.4 仍然存在的问题（未解决，如实记录）

* **偶尔会中途停住且没到目标**（实测：派「书房的桌子 (1)」，机器人从 (1.41,-5.14)
  走到 (2.21,-6.31) 后停住，没有 `tour_completed`）。多半是 follower 局部卡住
  → 停滞判定清空计划。**这时候重新派一次通常就能走完。**
* 目标落在**床/柜子等家具的贴墙侧**时，navmesh 上最近可走点可能在另一侧，
  路径会绕，表现为"走了一半停下"。



1. **续轮要重载场景**（数秒）。所以一程走完、接着派下一个地方时会有一次短暂停顿；
   同一场景内不会重载。**这是 habitat 的回合语义带来的，不是调度问题。**
2. **`episode_over` 仍会在每程结束时出现一次**（habitat 自己的判定），
   然后被续轮接住；事件流里看得到，属正常现象不是故障。
3. **地标是"大件家具"级别**，不是"任意点"。客人说"去房间中间那面墙"这类话对不上，
   得用清单里的名字（如「卧室的床」）。**要支持任意点**需要加"按相对位置描述目标"的能力。
4. **中文名依赖模型翻译的质量**。已在 `zh_glossary.json` 里冻结；要改就改那个文件
   （下次跑挖掘/翻译会复用，不会重翻）。
5. **旧地标表仍保留**（`data/landmarks.json`，指令锚点版），
   可用 `NAVLIVE_LANDMARKS` 切换回去做对比。
