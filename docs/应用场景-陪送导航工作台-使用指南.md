# 陪送导航工作台使用指南

适用于 2026-10-11 的导航侧工作台。入口：AGH Web 工作台（左栏就是**陪送导航看板**）。一台机器人，8 个已扫描楼层场景，一次任务跑一轮。**导航与位姿来自服务器上真实的 Habitat/MP3D + InternVLA-N1 闭环；装卸与交接是仿真业务，不在本工作台内。**

1. **打开工作台。** 先确认服务器在线（见文末命令），再打开 Web。左栏若已显示“路线① 导航失败诊断与恢复”和五套配置的对照表，说明看板拿到了数据；角标写“实时数据”是刚从服务器取的，写“静态快照”说明数据面暂时不可达，此时不要拿它做结论。看板是**只读**的，不在这里下单。

2. **下发陪送任务。** 在聊天里直接说清“去哪个场景、什么指令、跑几回合”，Agent 会起一次真实评估（会弹出审批，说明约 70 分钟 GPU）：

   > 在 4 个场景上各跑 13 回合，用最稳的恢复配置（撤掉早漂移/周期刷新、关掉碰撞看门狗），标签用 r1demo4。

   想省时间就先跑单场景小组：**13 回合 ≈ 17 分钟**。不愿意等也可以“不新跑”：直接让 Agent 分析已经跑完的那 15 个 run。

3. **看懂执行。** Agent 给的是逐场景表（Success/SPL/NE/碰撞/步数/System-2）+ 终止方式 + 重规划原因。三条判据要分清：

   - **跑满 ≠ 跑对**：先看回合数是否 52/52，再看**场景间 min/std/range**，最后才看池化均值。本项目最典型的失败是“某个场景崩掉”，均值看不出来。
   - **计划不是完成证明**：只有逐场景表落盘、且命令回执与看板数字对得上，才算这一轮完成。
   - **单场景数字不要外推**：每格 13 回合，SE ≈ 14pt，单场景差异要 >28pt 才算明显；结论只能讲方向 + 逐回合配对。

4. **途中干预或演示异常。** 陪送任务里最常见的两种异常，正好对应两条恢复通道：

   - **卡在墙边**（8 个动作内碰撞 ≥5 次）→ 碰撞通道要求“重新规划”，而**不是**让看门狗把整轮判死。要演示“判死有多糟”，就把 `watchdog=on` 跑一次，对比最差场景。
   - **一路走远**（12 个动作内朝目标改善 <0.3 m 或远离 >0.6 m）→ 进度通道要求重新规划。
   - 想直观看到“通道会怎么动”，不用新跑：让 Agent 调 `nav_recovery_options` 复算任意已有 run，它会给出触发点、原因、覆盖多少个失败回合。**它用的是与在线闭环同一份代码**，不是另写一套判据。

   中途插单的正确说法是**换清单再跑一轮**，例如“再加一个场景、只看新 4 个场景”，而不是在同一个 run 上改配置——一个 run 只有一份配置。

5. **看画面或问画面。** 带帧捕获的 run 在日志里保留了每个决策点的真实渲染帧路径。可以问：

   > 第 43 回合到底怎么走的？把距目标、碰撞、计划年龄、漂移都列出来。

   Agent 会返回逐决策表；要看图就说“把第 43 回合第 12 个决策点的帧找出来”（目前取图需要你打开那个路径，工作台还不直接显示图）。

6. **结束或开始下一轮。** 一轮 = 一个 run（一个标签、一份产物目录）。要停就停 tmux 会话（见文末命令）；要重来就换新标签再跑——“新一轮”不要复用旧标签，否则会覆盖产物。相机、看板刷新、聊天切换都不会影响正在跑的评估。

每轮上限：4 个场景 × 13 回合 = 52 回合；每个 episode 自身步数上限 501；52 回合实测约 60–70 分钟。**仿真步数与墙钟时间不是一回事**：日志里的“步数 501”是仿真步，实际墙钟取决于 GPU 排队。

看板或工具报错时，在服务器上：

```bash
# 数据面是否可用（不用 AGH 也能单独验）
cd /srv/agh-demo/agh-nav
PYTHONPATH=/srv/agh-demo/src \
  /srv/agh-demo/habitat-env/bin/python bin/agh_nav_probe.py
# ↑ 不带子命令会打一份速览（环境 + 最近 run + 五套配置头条）；完整命令见 --help

# 正在跑什么 / 跑到哪了
tmux ls
PYTHONPATH=/srv/agh-demo/src \
  /srv/agh-demo/habitat-env/bin/python bin/agh_nav_probe.py progress --run r1demo4
```

| 情况 | 操作 |
|---|---|
| 看板显示“静态快照” | 数据面断链：先跑上面的 status；恢复后在聊天里让 Agent 再调一次 `nav_compare_configs` |
| 工具报“实时数据面不可用” | 同上；缓存快照只能当参考，不能当结论 |
| 任务按钮/工具没反应 | 确认插件是启用状态（`package status` 里 `actual=running`） |
| 数字和 FINAL_TABLE 不一致 | 用 `nav_compare_configs` 重取；差异仍在就说明数据面读的是另一份产物，别直接引用 |
| 跑了很久没结果 | 评估在 tmux 里排队或 GPU 被别人占用；看 `nav_env_status` 的 GPU 与 eval_running |
| 想停掉本轮 | `tmux kill-session -t r1_<标签>`；然后在聊天里说明本轮作废 |

关掉浏览器或 SSH 只是断开查看，**不等于**停止服务器上的评估。

推荐分别演示三幕：① 基线对照（`R2A` vs `recovery_only` vs `guarded` 的 5×8 表）；② 最差场景 `QUCTc6BB5sX` 的“看门狗误杀 → 关掉后 0.1538→0.5385”；③ 两条通道介入（覆盖 12/13 失败回合、碰撞从 19.9 压到 8.0）。每幕各自一轮（一个标签），聊天与结果才清晰。

与「院递工作台」的关系：院递管“送到床边、交给护士”，本工作台管“走对路、走错能自愈”。两侧共用同一套 `FailureEvent` 契约（nav 侧 114 条事件 + 操作侧 12 条事件的合流已跑通），所以两边可以拼成一个“院区物资配送智能体”。
