# 语义地标层 —— 让「带客人去客厅沙发」这种话真能走

> 工作台能走到任意坐标，但**人说话用的是地方名**。这一层补的就是中间那段：
> 「名字 → 真实可达坐标」，并且把地标画在楼层图上、作为工具暴露给 Agent。

---

## 1. 为什么不是"手写一张坐标表"

先试过从数据里挖房间名，结论要如实写：

| 来源 | 结果 |
| --- | --- |
| habitat `semantic_scene.regions`（MP3D 语义区域） | **空**。这台 habitat 0.2.4 构建读不到 region 标注（实测 4 个场景全为空），所以拿不到"厨房/卧室"这种官方房间名 |
| 场景自带 R2R 指令 | **可用**。52 条指令本身就是人写的，里面到处是具体地点 |

于是做法是：**从指令里抽地点短语 → 锚到这条指令真正指代的坐标**。

### 锚定规则（这一步踩过坑，很关键）

一条指令里会出现多个地点短语，但**只有最后提到的那个才是终点**：

> "Walk into the **living room** and keep walking straight past the living room.
>  Then walk into the **entrance under the balcony**. **Wait in the entrance** to the other room."

最后提到的 `entrance` = 终点。所以：

* **最后一个**地点短语 → 该回合的 **goal** 坐标；
* 一开始我把"第一个地点短语"锚到 **start**，结果出现
  **"让机器人去客厅，它已经在客厅了，一步没走"**——因为 start 就是机器人出生的位置。
  所以现在**只用 goal 锚点**，每个地标都是真正要"走过去"的地方。

## 2. 产物

`navlive/data/landmarks.json`（4 个场景 / 28 个地标）：

```json
{
  "name": "沙发",
  "name_en": "couch",
  "position": [12.23, 0.13, 10.42],
  "source": "episode-goal",
  "episode_id": "220",
  "instruction": "…"
}
```

每个地标都带 `episode_id` 与原始指令——**可核对**：它为什么在这个位置，能追溯到哪一条真人写的指令。

| 场景 | 地标数 | 例子 |
| --- | --- | --- |
| `2azQ1b91cZZ` | 8 | 入口、拱门、桌子、沙发、壁炉、床、卧室、门厅 |
| `QUCTc6BB5sX` | 6 | 楼梯、厨房、床、卧室、桌子 |
| `TbHJrupSAjP` | 8 | 衣帽间、门口、卫生间、卧室、走廊、桌子、客厅、楼梯 |
| `zsNo4HB9uLZ` | 6 | 沙发、客厅、桌子、厨房、卧室、床 |

生成链（两条命令，都可复跑）：

```bash
# ① 从 habitat 里挖原料：语义区域（这次是空）+ 每回合的起点/终点/指令
CUDA_VISIBLE_DEVICES=0 PYTHONPATH=/srv/agh-demo/src \
  /srv/agh-demo/habitat-env/bin/python -u \
  navlive/landmark_probe.py --out navlive/data/landmarks_raw.json
# ② 抽短语 + 锚点 + 中文别名
python3 navlive/build_landmarks.py --in navlive/data/landmarks_raw.json --out navlive/data/landmarks.json
```

## 3. 接口与工具

| 入口 | 作用 |
| --- | --- |
| `GET /landmarks` | 不传参数 → 概览（每个场景几个）；传 `scene=` → 该场景全部地标 |
| `POST /resolve` | `{scene, names:[...]}` → 名字换坐标；解不出返回 **404 + 候选**（不猜） |
| `POST /action` `kind=goto_landmark` | `{names:["客厅","厨房"]}` → 解析成航点后真的走 |
| 工具 `navlive_landmarks` | Agent 用它看"这个场景有哪些叫得出名字的地方" |
| 工具 `navlive_goto_landmark` | Agent 用它按**地名**派活（收名字，不收坐标） |

`/state` 的快照里也带 `landmarks`（世界坐标），前端据此在地图上画点与名字；
服务端渲染的楼层图上也会画地标方块（文字尽力而为，见下）。

## 4. 实测（都在这台服务器上跑过）

```
# 名字 → 坐标（中文）
$ curl -s -X POST /resolve -d '{"scene":"2azQ1b91cZZ","names":["客厅","厨房"]}'
  ok = True
   客厅 -> [16.49, 0.13, 8.97]   (living room)
   厨房 -> [4.53, 0.13, -2.26]   (kitchen)

# 解不出的名字：明确失败 + 候选
$ curl -s -X POST /resolve -d '{"scene":"2azQ1b91cZZ","names":["游泳池"]}'
  ok = False | error = 解析 '游泳池' 失败：地标表里没有 '游泳池'
  候选: ['入口', '客厅', '拱门', '门口', '桌子']

# 地名真的驱动导航
$ curl -s -X POST /action -d '{"kind":"goto_landmark","names":["沙发"]}'
  ok=True label=沙发 target=[12.23, 0.13, 10.42]  resolved=[('沙发','couch')]
  → 机器人真的走了 25 步，位置从 (16.49, 8.97) 到 (12.49, 10.34)
```

工具自检 **64/64 通过**；AGH 里 `mcp status navlive` → **`tools=9`**，
新工具 `navlive_landmarks` / `navlive_goto_landmark` 都在目录里。

## 5. 限制（写作品文档时要一起写）

1. **地名册是"指令里提到过的地点"，不是完整房间清单**。这台 habitat 读不到语义区域标注，
   所以没有官方房间名；某个场景没被指令提到的房间（例如 `2azQ1b91cZZ` 的厨房）
   在册子里**就是没有**——此时接口会明确报"没有这个地标"并给候选，不会瞎走。
2. **同名地点在不同场景坐标不同**，甚至同一场景里"桌子"可能对应多个回合的不同桌子，
   目前按首次出现归并（`aliases` 去重）。
3. **中文名是人工别名表**（`build_landmarks.py` 里的 `ZH_ALIASES`），不是模型翻译；
   表里没有的短语会以英文原名出现在册子里。
4. **服务端地图上的地标文字可能画不出来**：这台机器上的 Pillow 9.5 默认字体渲染会抛
   `'ImageFont' object has no attribute 'getmask2'`。所以文字是"尽力而为"（失败就跳过），
   方块照画；**名字由前端自己在 SVG 上标**，不依赖服务端字体。
5. **走到成功点后本回合会结束**（habitat 的 VLN 判定：距目标 < 3 m 即 success=True，
   `episode_over`）。这时再派一个更远的地标不会执行；需要重新 `navlive_open` 开一个回合。
   这是仿真器的回合语义，不是工作台的 bug——演示时**一条任务一个回合**最顺。
