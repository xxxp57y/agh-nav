# 现场演示脚本｜路线① 导航侧（AGH + Agnes）

目标：**5 分钟内**让评委看到"自然语言 → 导航评估 → 环境反馈 → 失败后自主调整"的完整闭环，
且每一步都能点到真实数据。

准备工作（开始前 10 分钟做完）：

1. 在服务器上确认数据面可用：
   `PYTHONPATH=/srv/agh-demo/src <conda-python> /srv/agh-demo/agh-nav/bin/agh_nav_probe.py status`
2. AGH 实例已安装并启用 `@agh-nav/nav-agent-plugin`（工具 + Skill）与 `@agh-nav/nav-board-plugin`（看板）。
3. 仪表盘（左栏看板）应当已经显示 5 配置 × 8 场景对照表；角标是"实时数据"。
4. 兜底：断链时工具会自动回退到缓存快照并标注，**不要假装是实时数据**——直接说"现在读的是快照"。

---

## 第 1 幕｜"先看能不能跑"（30 秒）

> 用户：导航服务器现在什么状态？有没有人在占 GPU？

Agent 调用 `nav_env_status`，屏幕显示：GPU 占用、tmux 会话、正在跑的评估、磁盘余量、route1 是否可导入。

> 用户：我们跑过哪些导航评估？哪套恢复配置最好？

Agent 调用 `nav_list_runs`，列出 run 与池化指标。

**要讲的点**：评估不在本地跑，而是在有 Habitat/MP3D 与 InternVLA-N1 的服务器上；Agent 通过
工具而不是 shell 访问它，因此每一次调用都进 AGH 的工具记录（可审计）。

---

## 第 2 幕｜"这个 run 到底差在哪"（60 秒）

> 用户：帮我细看 r1grd4 这个 run：逐场景成功率、失败都是怎么结束的。

Agent 调用 `nav_run_summary` → 逐场景 Success/SPL/NE/碰撞/步数/System-2 + 终止方式分布 + 重规划原因直方图。

> 用户：第 43 回合智能体经历了什么？

Agent 调用 `nav_observe_episode`（run=r1grd4, episode=43）→ 逐决策：距目标距离、碰撞计数、
plan_age、轨迹漂移、几何分、是否重规划、原因。

**要讲的点**：这些就是"环境反馈"。判据的真相在这里已经能看出来——几何分（feedback_score）
在很多决策点上很小，而 `plan_age`（纯计时器）却一直活着；50% 的权重压在从未可用的信号上。

---

## 第 3 幕｜"把失败变成可分析的事件"（60 秒）

> 用户：把这些失败转成统一失败事件，标注类型和归因。

Agent 调用 `nav_failure_events` → `FailureEvent` 契约：`type`（N1 无可执行动作 / N2 进度停滞 /
N4 综合高 / N5 碰撞密度）+ `signals` + 一句话归因 + 证据 + 恢复动作 + 结果。

> 用户：现在的重规划触发判据到底有没有信息量？

Agent 调用 `nav_diagnose_triggers` → P@1/P@3/P@5（两种口径）+ 几何分 AUROC + 基率。

**要讲的点（本作品的硬结论）**：
- 几何分对真失败的 **AUROC ≈ 0.44（低于随机）**；
- 官方失败标签只覆盖 **11–15%** 的无动作事件；
- 因此"换判据"不是调参问题，而是**信号问题**——这为第 4 幕的两条通道提供了理由。

---

## 第 4 幕｜"失败之后该怎么调整任务"（90 秒，全场重点）

> 用户：如果 r1grd4 用碰撞密度和进度停滞这两条通道，会在哪些点要求重规划？覆盖多少失败回合？

Agent 调用 `nav_recovery_options` → 触发点清单（step + 原因）、触发密度、**覆盖 12/13 失败回合**、
回合级精度 0.4444（基率 0.2500）。工具里明确写着实现是
`route1.nav.channels.TriggerChannels`——**与在线闭环同一份代码**。

> 用户：那五套恢复配置在 8 个场景上的最终对照表呢？

Agent 调用 `nav_compare_configs` → 5×8 表 + 池化 Success/SPL + 最差场景/std/range + 代价。

**结论一句话**：按"要稳"的口径选 `recovery_only`（最差场景 0.1538 → **0.5385**、
std 0.2114 → **0.0914**）；要均值与低碰撞选 `guarded`（**0.7115**、碰撞 8.18/回合）。
原来报 0.66 的 R2A 在跨场景口径下**没有优势**。

---

## 第 5 幕｜"要不要再来一轮"（40 秒）

> 用户：用 recovery_only + 两条通道、关掉看门狗，在 4 个场景上再跑一轮。

Agent 调用 `nav_run_eval`（label=r1demo4）→ **AGH 弹出审批**：
`requiresApproval: always`，代价提示"52 回合 ≈ 60–70 分钟 GPU"。
批准后返回 tmux 会话名、产物路径、日志路径与参考值。

> 用户：跑到哪了？

Agent 调用 `nav_run_progress` → 完成回合数、逐场景计数、当前 Success、日志尾部。

**要讲的点**：写操作真的有门禁。工具层声明 `requiresApproval: always`，
AGH 在运行前把参数、代价、影响范围摆给用户看——这正是赛题"自主决策"要配的"可控"。

## 现场问答预备（评委最可能问的三件事）

| 问题 | 一句话回答 |
| --- | --- |
| 为什么不直接在 AGH 里跑仿真？ | 导航侧依赖 Habitat/MP3D 与 InternVLA-N1（GPU、几十 GB 资产），跑在服务器上；AGH 用插件把"发起/观测/诊断"变成工具，判据复用同一份代码，不需要搬迁仿真栈。 |
| 你们的 Agent 真的比原来强吗？ | 要看口径：在**跨场景**上，撤掉有害通道 + 关自杀式看门狗（`recovery_only`）把最差场景从 0.1538 提到 0.5385、场景间极差从 0.6923 压到 0.2308，且 System-2 调用一个没多；而单场景调出来的 R2A 优势不成立。 |
| 有没有失败/负结果？ | 有，而且是主动写的：语义 Monitor 在这批任务上 **AUROC ≤ 0.51、0 次 LOST**；"扩大恢复动作空间"只省 0–1.6% 的 System-2；这些都在 `docs/报告材料-导航侧.md` §3。 |
